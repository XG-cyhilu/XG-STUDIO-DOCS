参考Reference

VCL 的四条主线：目录即数据模型、后端可替换、启动是一条轮询管道、运行时统一。

Four threads in VCL: the directory is the data model, the backend is replaceable, launch is a polled pipeline, and the runtime is uniform.

目录即数据模型The directory is the data model

VCL 不维护自己的实例数据库，versions 目录就是数据库。识别规则只有一条：子目录里存在同名 .json 才算一个版本；中文与空格目录名照常支持。

VCL keeps no instance database of its own — the versions directory is the database. One rule decides recognition: a subdirectory counts as a version only if it contains a .json of the same name; Chinese and spaced names are supported as-is.

std::vector<VersionEntry> VersionScanner::Scan(const std::string& rootDir) const {
    std::vector<VersionEntry> out;
    for (auto& dir : ListDirectories(Join(rootDir, "versions"))) {
        std::string json = Join(dir, FileName(dir) + ".json");
        if (!Exists(json)) continue;                  // 没有同名 json → 不是版本
        VersionEntry e = PeekHeader(json);            // 只读 id/type/inheritsFrom 等头部
        if (!e.id.empty()) out.push_back(e);          // 坏 JSON 跳过并记日志
    }
    return out;
}

版本隔离的判定同样落在目录上，而不是配置里的开关：

Isolation is also decided by directories rather than a config switch:

if (Exists(join(versionDir, "mods")) || Exists(join(versionDir, "config"))
 || Exists(join(versionDir, "saves")) || Exists(join(versionDir, "options.txt")))
    mode = VersionDir;     // 版本目录里已有游戏数据 → 隔离
else
    mode = RootDir;        // 否则与所有版本共享
// UI 上永远可手动改，导入不做不可逆判断

私有元数据只放在 versions\<folder>\.vcl\（instance.json 与可选图标），PCL 不会读它；全局配置与缓存放在 %APPDATA% / %LOCALAPPDATA%，不进游戏目录。

Private metadata lives only in versions\<folder>\.vcl\ (instance.json plus an optional icon), which PCL never reads; global config and caches live under %APPDATA% / %LOCALAPPDATA%, never inside the game directory.

后端可替换A replaceable backend

四个能力被抽成一个纯虚接口，界面阶段接假实现，真实阶段接 Rust 封装。页面代码只认接口，因此替换后端不触碰 UI。

Four capabilities sit behind one pure virtual interface. The UI phase uses a fake implementation; the real phase uses the Rust wrapper. Pages only know the interface, so swapping backends never touches the UI.

struct IBackend {
    virtual ~IBackend() = default;
    virtual std::vector<VersionEntry> ListVersions(const RootInfo& root) = 0;
    virtual bool Install(const InstallRequest& req, IProgressSink& sink, std::string& err) = 0;
    virtual bool Launch(const LaunchRequest& req, ILaunchSink& sink, std::string& err) = 0;
    virtual std::vector<JavaInfo> FindJava() = 0;
};

// 启动时二选一：Mock 提供 2~3 个假实例、0.3s 一跳的假进度
std::unique_ptr<IBackend> backend = useMock ? MakeMockBackend() : MakeLightyBackend();

两个 sink 都是轮询式：Poll() 取事件，不注册回调。这样 UI 线程不会被 Rust 侧线程反向调用，也不需要处理重入。

Both sinks are polled: Poll() pulls events and no callback is registered. The UI thread is never called back from Rust threads and never has to handle reentrancy.

启动是一条管道Launch is a pipeline

启动流程固定为八步，每一步只做一件事；安装走完全相同的形状，只是把 launch 换成 install，结束时重扫版本目录。

Launch is a fixed eight-step pipeline, one job per step. Installation has exactly the same shape with install in place of launch, followed by a rescan of the versions directory.

1  RootManager.Load(global.json) → 选中 Root
2  VersionScanner.Scan(root)      → 版本列表
3  InstanceStore.Load(folder)     → instance.json（缺失即默认）
4  组装 LaunchRequest(root, folder, gameDir, memoryMb, jvmArgs, javaPath, 离线身份)
5  backend.Launch(req, sink)      → lighty_launch_start(...)
6  UI 每 200ms: lighty_launch_poll → 状态 / 日志 / 进度 → LogHub + 日志面板
7  Finished: 写回 lastPlayedAt / totalPlayTimeSec
8  非 0 退出且日志含 Exception → 提供「查看日志 / 打开目录」
while (running) {
    LightyEvent ev;
    while (lighty_launch_poll(handle, &ev)) {   // 非阻塞，事件队列固定容量
        switch (ev.kind) {
        case Progress:    progress = ev.progress; break;   // done / total / bytesPerSec
        case Log:         logHub.Append(ev.level, ev.text); break;
        case StateChanged: state = ev.state; break;
        case Finished:    running = false; code = ev.code; break;
        case Failed:      running = false; err = ev.msg; break;
        }
    }
    Sleep(200);                                   // 与 Snapshot() 同频
}

进度用原子计数，事件队列容量固定：满时丢弃并计数，绝不阻塞 Rust 侧工作线程——与 XGDL、XGLOG 是同一套口径。

Progress uses atomic counters and the event queue has a fixed capacity: on overflow it drops and counts instead of blocking the Rust worker — the same policy as XGDL and XGLOG.

跨语言边界The cross-language boundary

Lighty 是 Rust 静态库，边界规则必须死守，否则问题会以「随机崩溃」的形式出现：

Lighty is a Rust static library; boundary rules must be strict, or failures show up as random crashes:

  • 头文件只有 C 类型（const char* UTF-8、int32_t、uint64_t、不透明句柄），不出现 std::string、引用或 enum class。
  • Headers expose C types only (const char* UTF-8, int32_t, uint64_t, opaque handles) — no std::string, references or enum classes.
  • Rust 每个入口包 catch_unwind，panic 转错误码，绝不跨边界展开。
  • Every Rust entry point wraps catch_unwind and turns panics into error codes; unwinding never crosses the boundary.
  • 错误用「返回码 + last_error(handle)」；字符串由 Lighty 持有，调用方只读。
  • Errors use a return code plus last_error(handle); strings are owned by Lighty and read-only for the caller.
  • 内存谁分配谁释放；跨边界只传调用方缓冲或 Lighty 分配 + Lighty 释放。
  • Whoever allocates frees; across the boundary only caller buffers or Lighty-allocated plus Lighty-freed memory is passed.
  • 全工程 /MD，Rust 侧 crt-static 关闭，保证两侧共用同一份 CRT。
  • The whole project uses /MD with crt-static disabled on the Rust side, so both sides share one CRT.
